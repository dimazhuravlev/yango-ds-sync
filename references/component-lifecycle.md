# Жизненный цикл компонента в ДС: перенос, развитие, вывод из оборота

Цель каждого шага: ни один инстанс в макетах не должен сломаться или молча поменяться.

## Перенос компонента между файлами ДС

API не переносит компонент с сохранением ключа: `createComponent` даёт новый ключ, пересборка мастера меняет пути
узлов → слетают глубокие оверрайды во всех инстансах. Ключесохраняющий путь — только интерфейс Figma:

1. Слепок макетов-потребителей (`00c-snapshot.js`) — до всего.
2. Пользователь выделяет кластер (мастер + приватные части + их сеты), **Cmd+X** (не Cmd+C), вставляет в целевой файл,
   публикует целевой файл, затем исходный.
3. В целевом файле сеты получают новые ключи; в исходном оригиналы живут как «удалён, удерживается инстансами».
   Для опубликованных компонентов Figma регистрирует редирект старый ключ → новый (`importComponentSetByKeyAsync(старый)`
   резолвится в новый); потребители подхватывают его при принятии обновлений.
4. Приватные `. /` компоненты редиректа не получают: ручные `instance swap` на них остаются на призраках —
   перепривязать (`recipes/relink-ghost-slots.js`) и в ДС, и в макетах.
5. После принятия обновлений — `01b-compare-with-snapshot.js`. Норма — только изменение счётчиков оверрайдов.

## Развитие сета на месте (безопасно)

- Добавление вариантов, переименование сета, осей и значений не меняет ключ сета и id вариантов — инстансы не
  затрагиваются. Поэтому объединять сеты развитием существующего, а не новым сетом (новый = свап всех инстансов).
- Переименование слоёв в мастере безопасно (оверрайды держатся по id), но у инстансов с подменённым слоем имя слоя =
  имя варианта.
- Удаление слоя или новая обёртка в мастере укорачивают путь и отвязывают оверрайды (картинки, тексты) во всех
  инстансах.
- Общая ось (`Product = Yango | YaPS`) вместо дубликата компонента: у новых вариантов должны совпасть id свойств
  (`Icon glyph#1269:0`), тогда колонки свойств сливаются.
- Вариант, удалённый из сета, продолжает жить в инстансах призраком — закрывается только миграцией инстансов.

## Вывод из оборота

1. Перепись использования по всем страницам всех файлов ДС (с заходом в инстансы и скрытое) и по макетам —
   `recipes/usage-before-delete.js` (в ДС) и `03-census.js` с ключом (в макетах). Считать использование внутри других
   компонентов.
2. Записать карту «старый ключ / вариант → чем заменяем» в описание нового компонента или в `references/twins.md`: после
   удаления мастера панель ассетов его не покажет.
3. Мигрировать инстансы (сначала ДС, потом макеты), пересчитать использование → 0.
4. Лишнее удалять сразу, а не помечать крестом, — при нулевом использовании. Крестик `❌` нужен только архивной ДС,
   чтобы руками не брали устаревшее; у приватных — после точки (`. / ❌ spinner`), иначе компонент станет публичным.
5. Пользователь публикует библиотеку (диалог покажет «removed components»).

Инстансы удалённого мастера в чужих файлах не ломаются и не отсоединяются: Figma хранит данные удалённого
компонента в файле, они рендерятся как прежде; скрипты их видят (`getMainComponentAsync()` работает, ключ читается,
импорт по ключу — not found). Теряется только обновление через библиотеку.

## Публикация

- API не публикует и не принимает обновления — просить пользователя одной фразой («опубликуй Library, затем прими
  обновления в макете и напиши „готово“»).
- Порядок: библиотека-источник → библиотеки-потребители → макеты.
- Перед просьбой проверить в файле ДС `getPublishStatusAsync()`: `CHANGED` / `UNPUBLISHED` — свап внутри ещё не уехал.
- В потребителе `importComponentSetByKeyAsync(ключ)` отдаёт опубликованную версию — по числу вариантов видно, доехало ли.
- Правки, сделанные внутри инстансов чужих носителей, обновление библиотеки откатывает — чинить носитель.

## Цвета в мастерах Library

`recipes/library-colors-to-variables.js` (в файле Library): сырой цвет → переменная Theme только при полном совпадении
hex и альфы в тёмной теме для всех продуктов; цвет без переменной, System Elements, варианты Light, акцент не
трогать. Тяжёлые страницы — по срезам сетов. После — публикация.

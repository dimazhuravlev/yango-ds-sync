# yango-figma-work: проектные задачи на ДС Платформа

Исполнитель — Claude с Figma MCP; заказчик — продуктовый дизайнер. Задача про конкретные экраны, флоу и компоненты.
Почти любая задача сводится к одному из двух:
- **собрать** компонент / экран / флоу из существующих компонентов ДС Платформа (экран — композиция инстансов, а не
  рисунок; руками только то, чего в ДС нет и что задача прямо требует, и то на переменных);
- **доработать ДС** — создать или расширить компонент ДС Платформа (вариант, свойство, состояние), а потом собрать из него.

**Общее ядро — скилл `yango-ds-sync`** (тот же репозиторий, `~/.claude/skills/yango-ds-sync/`). Перед первым `use_figma`:
загрузить `figma-use`; прочитать из ядра `references/sources.md` (файлы ДС, ключи библиотек, коллекции),
`references/text-and-color.md` (стили, переменные, режимы бренда), `references/rules.md` → «Как спрашивать»,
`references/figma-api-gotchas.md`. Опись компонентов ДС — `keys/library-components.txt`, двойники — `references/twins.md`.

## Окружение

Приложение Claude, вкладка Code, рабочая папка `~/Repos` (там память с правилами владельца); одна задача — одна сессия.
Figma MCP с правом записи, шрифты Yango / YS загружены в аккаунт Figma (README репозитория → шрифты).

## Что нужно от дизайнера

Ссылка на экран, страницу или компонент (node-id); что сделать — словами, образцом (ссылка на похожее), кодом / ссылкой на
прототип; бренд, если из файла не ясно. Неясно — один пакет вопросов до записи, с картинками.

## Процесс

1. **Понять исходное.** Дерево узла (компоненты и варианты, геометрия, авто-лейаут, режимы `Product` на предках) и
   скриншот. Найти образец: данный дизайнером или очевидный (такое же состояние в другом продукте, соседние экраны флоу).
2. **План текстом** — что меняется, из каких компонентов ДС (сет + вариант + свойства), что локально и почему, что
   добавляется в ДС. Через результат, коротко. Крупное или спорное — подтверждение до записи.
3. **«Стало» до записи.** Новый экран / состояние — рядом с исходным (в том же ряду, с тем же шагом, режимами и
   оформлением страницы), исходный не трогать. Правка существующего — превью на временной копии
   (`yango-ds-sync/scripts/recipes/preview-change.js`). Картинки «было → стало» прямо в чат (`yango-ds-sync/scripts/shot.sh`).
4. **Запись** по частям; каждая — с проверкой в том же вызове (размеры блоков, тексты, видимость) и откатом при
   расхождении. Тяжёлое — кусками, после обрыва связи перечитать состояние перед повтором.
5. **Проверки ядра** по новому / изменённому (`ONLY` = id): `06-text-styles.js` 'report' (тексты на стилях ДС),
   `recipes/text-weights.js` (Medium / Semibold), `07b-colors-to-variables.js` 'report' (цвета на переменных), `06a`
   'report' (режим бренда), `recipes/icon-size-audit.js`, `recipes/unwrap-wrappers.js`, имена слоёв по роли.
6. **Отчёт** (шаблон ядра): что сделано — ссылками и картинкой результата; что решить — «было → стало».
7. **Пополнить скилл**: новый тип задачи или грабля — строкой в «Типовые задачи» и файлом в `references/`, скрипт — в
   `scripts/` с CONFIG наверху; ветка + PR в репозиторий.

## Доработка ДС Платформа (направление 2)

Только когда задача прямо про это или без нового варианта экран не собрать (тогда — вопросом). Работа в файле
ДС Платформа (`b8maDlvYFFs2vagJxwxc4A`): расширять существующий сет (вариант, свойство), а не плодить новый; имена свойств
и вариантов — как у соседей (`RTL=off|on`, `Size=`, `State=`, `Active=…`); все цвета, тексты, отступы, радиусы — на
переменных и стилях 🌈 Стилей; оба бренда через режимы `Product` и RTL-вариант, если он есть у соседей. Порядок жизни
компонента, публикация, перенос, удаление — ядро `references/component-lifecycle.md`; по сборке вариантов и привязке
токенов — скилл `figma-generate-library`. Опубликовать — дизайнер (API не умеет); после — «Update all» в проекте и сборка.

## Строгость по типу файла

- Чистовики (🏁 … Current State) и проектные файлы: только компоненты, стили и переменные ДС; локальные слои — когда
  задача требует (скелетон, иллюстрация), всегда на переменных. Без просьбы ничего не удалять и исходные экраны не менять.
- Черновики и песочницы: можно быстрее, но то, что не из ДС, назвать в отчёте.
- Локальные мастер-компоненты в проекте не создавать без просьбы; новое для общего пользования — в ДС Платформа.

| Объединить наборы ДС в один с вариантами | копии вариантов → один набор, переключатели с прежними именами, старые с ❌ → замена в чистовиках | `references/ds-components.md` |
| Карточка с высотой по пропорции (в строке списка) | внутренний `size` FILL + замок пропорций в мастере, в строке слот фиксированной ширины | `references/ds-components.md` |
| Вариант ДС с локальной копией атома → инстанс атома | новый вариант рядом (старый — `… old`), сверка попиксельно, публикация → свап в макетах со сверкой каждого инстанса → старый удалить | `references/ds-components.md`, `scripts/swap-variant-verified.js` |
